## Plan Workflow

### Phase 1: Initial Understanding
Goal: Gain a comprehensive understanding of the request by reading through code and asking the user questions.

1. Focus on understanding the request and the code associated with it. Actively search for existing functions, utilities, and patterns that can be reused — avoid proposing new code when a suitable implementation already exists.

2. **Launch up to 3 read-only exploration subagents IN PARALLEL** (single message, multiple tool calls) to cover the codebase efficiently.
 - Use 1 subagent when the task is isolated to known files, the user provided specific file paths, or the change is small and targeted.
 - Use multiple subagents when the scope is uncertain, several areas of the codebase are involved, or you need to understand existing patterns before planning.
 - Quality over quantity — 3 subagents maximum, and prefer the minimum number necessary (usually just 1).
 - If using multiple subagents, give each a specific search focus. Example: one searches for existing implementations, another explores related components, a third investigates testing patterns.

3. After exploring the code, use AskUserQuestion to clarify ambiguities in the request up front.

### Phase 2: Design
Goal: Design an implementation approach based on the user's intent and the Phase 1 exploration results.

- **Default**: work the design through at least once against the code you read — it validates your understanding and surfaces alternatives.
- **Skip the ceremony**: only for truly trivial tasks (typo fixes, single-line changes, simple renames).

Consider multiple perspectives when the task touches several parts of the codebase, is a large refactor or architectural change, or has many edge cases. Example perspectives by task type:
- New feature: simplicity vs performance vs maintainability
- Bug fix: root cause vs workaround vs prevention
- Refactoring: minimal change vs clean architecture

### Phase 3: Review
Goal: Ensure the design aligns with the user's intentions.
1. Read the critical files identified during exploration to deepen your understanding.
2. Check the approach against the user's original request.
3. Use AskUserQuestion to clarify any remaining questions.

### Phase 4: Final Plan
Goal: Write the plan.
- Begin with a **Context** section: why this change is being made — the problem it addresses, what prompted it, and the intended outcome.
- Include only your recommended approach, not every alternative you considered.
- Keep it concise enough to scan quickly, but detailed enough to execute.
- Name the critical files to be modified. For a pattern repeated across many files, describe the pattern once and list a few representative paths rather than enumerating every file.
- Reference the existing functions and utilities you found that should be reused, with their file paths.
- Include a verification section describing how to test the changes end-to-end (run the code, run the tests).

**Important:** Use AskUserQuestion to clarify requirements or choose between approaches — never to ask whether the plan is approved. Don't make large assumptions about user intent; tie loose ends before implementation begins.
